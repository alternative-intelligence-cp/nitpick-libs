# nitpick-tui against compiler 7e91730 (landings 83–103) — an audit

**Verdict.** The plan is mostly unaffected. It specifies no floating point, `comptime`, macros, templates or `#unreachable`, and it cites no diagnostic whose behaviour moved. Three things need work before cycle 0.0 runs:
- **Reader signatures.** Every byte-reading signature is spelled plain `uint8[]`, and landing 103 makes `string_bytes` return `fixed uint8[]`, which no plain `uint8[]` slot accepts. Probe 14 is built on that now-false assumption.
- **The restore record.** The restore record's byte array in `fixed` module state runs into the 98/103 rule that a `fixed` slice is read-only.
- **The LLVM pin.** The LLVM pin is stale: the compiler now pins 20.1.8.

Compiler-side facts below are measured from its documents. Statements about what the plan's functions will do are inferred, because no source exists yet.

## FINDINGS

**TL-1 — Reader signatures are plain `uint8[]`, so a `string_bytes` caller is TYPE-007** *(changes a plan; cycles 0.0.4, 0.2, 0.3, 0.16)*
- Library:
  - `specs/INPUT_MODEL.md:106`: `pub func:input_feed = NIL(Decoder->:d, uint8[]:bytes, int64:now_ns);`
  - `specs/TEXT_MODEL.md:230-231` and `DECISIONS.md:644` (T-106): "`text_width(uint8[]) → uint32` over a string and `cluster_width(uint8[]) → uint8`". Also `roadmap/0.2/README.md:59`.
  - `specs/TEXT_MODEL.md:71` (X-7): the segmenter is "an incremental function over a byte slice".
  - `roadmap/0.0/0.0.4.md:69`: "`view()` hands a borrowed `uint8[]` for the write path."
- Compiler:
  - `specs/TYPE_REFERENCE.md:1233-1243`: "`fixed T[]` is the READ-ONLY VIEW … A plain `T[]` converts to it … and it converts back to nothing (`NITPICK-TYPE-007`) … PRODUCED by … `string_bytes` (always …)".
  - `specs/DECISIONS.md:22813-22815` (D-351): "a `string_bytes(s)` result goes where a `fixed uint8[]` goes … and converts to no plain `uint8[]`".
  - `NOTICES.md` row 103: "a function that takes such a view and only reads it declares `fixed uint8[]:`".
- What should change:
  - Declare every read-only byte parameter `fixed uint8[]`. That covers `input_feed`, `text_width`, `cluster_width`, the UTF-8 decoder and the segmenter.
  - A plain slice still converts to it, so callers holding a `Bytes` or the staging buffer are unaffected.
  - `Bytes.view()` (0.0.4:69) should return `= fixed uint8[] (…)`, the bare-position spelling D-350 gives.
  - T-106 is a decision, so amend it with a dated note rather than rewriting it.
- Inferred: the committed-fixture tests (TESTING.md:82-93) and the 0.16 fuzz drivers will get their bytes from files or strings, so they would hit TYPE-007 against a plain signature.

**TL-2 — Probe 14 is built on a premise that is now false** *(blocks cycle 0.0; the probe set is execution-grade)*
- Library:
  - `roadmap/0.0/0.0.0.md:298`: "`string_bytes(s)` into a function that decodes it".
  - `0.0.0.md:304`: "the whole text layer takes `uint8[]` and every widget hands one down".
  - `roadmap/0.0/README.md:57` carries the same probe.
- Compiler: D-351 and TYPE_REFERENCE:1242, as quoted in TL-1.
- What should change:
  - Probe 14's decoder takes `fixed uint8[]`.
  - Add a control: a plain `uint8[]` decoder fed by `string_bytes` is expected TYPE-007.
  - Add a write through the view, expected TYPE-086, and the address of an element, expected TYPE-071.
  - Rewrite the "Matters because" sentence.
- Why it matters: as written, a plain-slot decoder would return REFUSED TYPE-007 at the "legal" edge, and the verdict would be recorded against the wrong cause (P-3, P-4).

**TL-3 — The restore record's byte buffers in `fixed` module state** *(changes a plan; cycles 0.0 probe 12 and 0.1.2)*
- Library:
  - `specs/TERMINAL_MODEL.md:209-217`: a `fixed` module record with `uint8[36]:saved_termios`, "the mutable interior … reached through an atomic".
  - `TERMINAL_MODEL.md:225`: "a fixed 256-byte static buffer" built in `ntui_restore`. Also `roadmap/0.1/README.md:68`.
  - `roadmap/0.0/0.0.0.md:272-273`: probe 12 asks for "a module-level `fixed` binding holding … a fixed-size byte array; written from ordinary code".
- Compiler:
  - `specs/TYPE_REFERENCE.md:2030-31`: a `fixed` module binding's "initialiser is the only place it can be written".
  - `TYPE_REFERENCE.md:2075`: a write into a part of a `fixed` binding is `NITPICK-TYPE-086` (DEF-106).
  - `TYPE_REFERENCE.md:1240-1242`: ranging a `fixed` array, or a slice held in a `fixed` aggregate, is produced as `fixed T[]`.
  - `NOTICES.md` F44: DEF-246 listed "a `fixed` module array ranged into a plain view and written" as a `MachineFault` in safe code, and landing 103 closes it.
- Inferred: a plain-slice builder over the module buffer is now TYPE-007, and element writes are TYPE-086. Only the `atomic<int32>` word is writable from ordinary code.
- What should change:
  - The probe must ask separately whether the bytes can be written at all, and by what route, not only the atomic word.
  - The 0.1.2 builder cannot take a plain `uint8[]` over module storage.
  - The probe's own "negative verdict is the most expensive" warning (0.0.0:282-285) now applies to the byte half specifically.
- I did not find a compiler document that settles whether an interior byte array is writable. That is OPEN-1.

**TL-4 — The LLVM pin is 20.1.2 in every document and in the manifest** *(blocks cycle 0.0.1 and 0.0.2 as written)*
- Library:
  - `roadmap/0.0/0.0.1.md:53`: "installs LLVM 20.1.2".
  - `roadmap/0.0/README.md:66` and `0.0.0.md:355`: "must be the pinned 20.1.2".
  - `roadmap/0.0/0.0.2.md:49`: `toolchain.py` "refuses a mismatch against `[toolchain] llvm`".
  - Outside the audited set: `nitpick.toml:40` (`llvm = "20.1.2"`), `CLAUDE.md:105`, `README.md:124`.
  - `nitpick.toml:35-36` says it is "pinned to the exact patch release the compiler pins".
- Compiler:
  - `specs/TCB.md:53`: "LLVM 20.1.8 `llc`, `ld.lld` … — 20.1.2 from 1.4.5 until D-349 (2026-10-08)".
  - `BOARD.md:32`: "the pin is `7e91730` and its LLVM is the machine's 20.1.8".
- What should change: move all of these to 20.1.8. As written, the harness's refusal check would refuse the correct toolchain once the pin moves.

**TL-5 — The post queue's mutex has no stated lock level** *(wording; cycle 0.10.4)*
- Library: `specs/EVENT_MODEL.md:183-185`: "`ntui_post` appends to a mutex-guarded fixed-capacity queue and writes eight bytes to the eventfd". Also `roadmap/0.10/README.md:63`.
- Compiler: `specs/CONCURRENCY_REFERENCE.md:394-396`: "`LEVEL` is checked (1.6.1e step 3 …) … a wait at or below a held level is `NITPICK-LOCK-001`". NOTICES row 83 adds LOCK-001 and LOCK-002.
- What should change: the cycle plan should name the mutex's level. It should also say the eventfd write happens after release, or is not a wait.
- Nothing in the documents conflicts. The queue is a mutex plus an array, not a `Channel`, so this is only a gap that 83's checks now make visible.

**TL-6 — The compiler's state is described as cycle 1.5** *(wording; cycle 0.0)*
- Library: `roadmap/0.0/0.0.0.md:23`: "The compiler is at `../../nitpick`, cycle 1.5 (verification)".
- Compiler: `NOTICES.md` rows 83–103 are all "1.6.1e".
- What should change: update the sentence, or drop the cycle number.

**TL-7 — "fixed" is used as a size adjective next to a loaded keyword** *(wording; cycles 0.1, 0.3, 0.10)*
- Library:
  - `specs/TERMINAL_MODEL.md:445`: "a fixed 4096-byte staging buffer".
  - `roadmap/0.1/README.md:68`: "fixed 256-byte static buffer".
  - `roadmap/0.0/README.md:47`: "stored in a fixed array".
- Compiler: `specs/TYPE_REFERENCE.md:1240-1243`, as quoted in TL-3.
- What should change: write "fixed-size" where the size is meant, or an implementer may declare the staging buffer `fixed`. A `fixed` staging buffer would make the `read` into it a TYPE-086.

## OPEN

- **OPEN-1.** I found no compiler document that settles whether a `fixed` module struct's non-`fixed` interior array can be element-written. TYPE_REFERENCE:2030-31 and :2075 say no. D-211 and the existing "mutable interior" idiom say it goes through an atomic. Only probe 12 can settle it, and TL-3 is the reason to widen it.
- **OPEN-2.** `0.0.0.md:65` records "`NITPICK-LEX-003` with `NITPICK-RESOLVE-005` behind it" for `mod:01_argv;`. Landing 101 (row 101, faces b and d) changed second reports after a refused integer literal. I could not tell from the documents whether the RESOLVE-005 behind LEX-003 survives. The sentence is a historical measurement, but re-measure it before it is reused as a diagnostic fixture.
- **OPEN-3.** `Bytes.view()` returns a slice of the `Bytes`' own `buffer`. TYPE_REFERENCE:1230-1232 says a slice "passes down the call stack and never up". The plan calls this legal and probe 02 tests the return case. That predates 83 and is not a finding of this audit, but TL-1 touches the same return type.
- **OPEN-4.** I did not open `.internal/handoff_33/libs_moved_103.txt`, which lists every library file moved by landing 103. It would confirm that no ntui file is named, though ntui has no source yet.
